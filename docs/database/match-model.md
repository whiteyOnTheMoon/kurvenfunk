# Match Model

## Status

Task: 067 – Match Model

Status: Defined

## Purpose

This document defines the canonical football match domain model used by Kurvenfunk.

A Match represents one scheduled or played football match between two Clubs within a specific Season and Competition.

The Match entity is provider-independent.

External sports providers may supply fixture, result, status, and timing data, but provider-specific identifiers and payloads are not part of the canonical Match identity.

The Match model is designed to support:

- scheduled fixtures
- upcoming matches
- completed matches
- postponed matches
- cancelled matches
- abandoned matches
- results
- matchday-based competitions
- competition and season filtering
- club fixture lists
- club match history
- sports data imports
- future live match functionality
- article and discussion references
- standings calculation

This task defines the domain model only.

No Prisma migration is created as part of Task 067.

---

## Scope

The Match domain model covers:

- Match identity
- Home Club
- Away Club
- Competition
- Season
- Kickoff
- Matchday
- Match status
- Match score
- temporal match information
- domain integrity rules
- relationships to existing domain entities
- provider-independent representation

The Match model does not define:

- individual match events
- goals as separate entities
- cards during a match
- substitutions
- lineups
- player statistics
- referee data
- venue data
- live commentary
- betting data
- provider-specific raw payloads

Those concerns may be introduced by later domain models if required.

---

## Entity

### Match

A Match is the canonical Kurvenfunk representation of a football fixture or played football match.

A Match always belongs to:

- one Competition
- one Season
- one home Club
- one away Club

A Match has:

- one canonical internal identifier
- one scheduled kickoff
- one match status
- zero or one currently known score
- an optional matchday

The Match entity must remain independent from any external sports-data provider.

---

## Attributes

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | UUID | yes | Immutable internal Kurvenfunk Match identifier |
| `homeClubId` | UUID | yes | Reference to the home Club |
| `awayClubId` | UUID | yes | Reference to the away Club |
| `competitionId` | UUID | yes | Reference to the Competition |
| `seasonId` | UUID | yes | Reference to the Season |
| `kickoff` | Timestamp | yes | Scheduled kickoff instant |
| `matchday` | Integer | no | Competition matchday/round number where applicable |
| `status` | MatchStatus | yes | Current canonical status of the Match |
| `homeScore` | Integer | no | Current/final score of the home Club |
| `awayScore` | Integer | no | Current/final score of the away Club |
| `createdAt` | Timestamp | yes | Creation timestamp |
| `updatedAt` | Timestamp | yes | Last modification timestamp |

---

## Match Identity

`Match.id` is the canonical internal identity of the Match.

The identifier:

- is generated by Kurvenfunk
- is immutable
- is independent of external provider identifiers
- must never be replaced when provider data changes
- is used by other Kurvenfunk entities when referring to a Match

Provider identifiers must not become the primary identity of a Match.

For example, the same real-world match may later be imported from multiple providers.

Those providers may use different identifiers.

The Kurvenfunk Match remains the same domain entity.

---

## Home Club

`homeClubId` references the Club representing the home side.

The referenced Club must be an existing canonical Club.

The Match stores the relationship to the Club rather than copying:

- club name
- short name
- logo
- colors
- aliases

Club information remains owned by the Club domain model.

A Match therefore uses the current canonical Club entity.

---

## Away Club

`awayClubId` references the Club representing the away side.

The referenced Club must be an existing canonical Club.

The Match stores the relationship to the Club rather than duplicating Club information.

---

## Home and Away Integrity

A Match must not reference the same Club as both home and away side.

Therefore:

`homeClubId != awayClubId`

is a mandatory domain invariant.

This rule prevents invalid matches such as:

SK Rapid Wien vs SK Rapid Wien

unless a future competition format explicitly requires a different domain concept.

The standard Match model assumes two distinct Clubs.

---

## Competition

`competitionId` references the canonical Competition.

The Competition represents the competition itself.

Examples:

- Österreichische Bundesliga
- ÖFB Cup
- UEFA Champions League

Competition identity is independent from a particular Season.

A Match therefore does not store a competition name directly.

---

## Season

`seasonId` references the canonical Season.

A Season represents a specific edition of a Competition.

The Match belongs to the Season in which it is scheduled or played.

The Season therefore provides the temporal competition context.

---

## Competition and Season Consistency

A Match references both:

`competitionId`

and:

`seasonId`

The referenced Season must belong to the referenced Competition.

The Match must never represent a Season from a different Competition.

For example, a Bundesliga Match must not reference:

- Bundesliga Competition
- Austrian Cup Season

The Competition/Season relationship is owned by the Season model.

The Match references the canonical Season and Competition for efficient domain queries and explicit Match context.

The application must validate that:

`season.competitionId == match.competitionId`

before creating or accepting a Match.

Where practical, database-level integrity should also prevent inconsistent references.

---

## Kickoff

`kickoff` represents the scheduled kickoff instant of the Match.

The value is an absolute point in time.

The domain must not depend on the server's local timezone.

PostgreSQL should store the value using a timezone-aware timestamp representation.

The application should expose localized representations to users where appropriate.

For example, a Match may internally represent:

2026-08-15T18:30:00Z

while the frontend displays the corresponding local time.

---

## Scheduled Kickoff

`kickoff` represents the currently canonical scheduled kickoff.

If a Match is postponed and a new kickoff is confirmed, the Match's `kickoff` value may be updated to the new scheduled time.

The system should not create a second Match merely because the original kickoff time changed.

A postponed Match remains the same Match unless the external competition context identifies it as a genuinely different fixture.

---

## Kickoff Changes

External sports providers may send multiple kickoff changes.

Kurvenfunk must normalize those updates onto the canonical Match.

Examples:

Original:

2026-08-15 18:30

Postponed:

2026-08-16 17:00

The canonical Match remains the same entity.

Only the current scheduled kickoff is updated.

Historical kickoff changes may later be recorded by a dedicated history/audit model if required.

The Match model itself does not require kickoff history.

---

## Matchday

`matchday` represents the numerical matchday or round number when the Competition format supports such a concept.

Examples:

1

2

3

10

30

The field is optional because not every competition uses a simple numerical matchday.

For competitions where the concept is not applicable, `matchday` may remain `NULL`.

---

## Matchday Semantics

`matchday` must not be interpreted as:

- calendar week
- date
- kickoff time
- competition stage
- round name

It represents the canonical numerical matchday/round value supplied or determined by the competition context.

More complex competition structures may later require additional fields such as:

- stage
- group
- round
- leg

Those are outside the initial Match model.

---

## Match Status

The Match has a canonical status.

The initial status set is:

| Status | Meaning |
|---|---|
| `SCHEDULED` | Match is scheduled but has not started |
| `LIVE` | Match is currently in progress |
| `FINISHED` | Match has been completed |
| `POSTPONED` | Match was postponed and has not yet been completed |
| `CANCELLED` | Match was cancelled and will not take place as currently represented |
| `ABANDONED` | Match started or was scheduled to start but was abandoned |

The exact enum representation will be implemented later in Prisma.

---

## Status: SCHEDULED

`SCHEDULED` means:

- the Match is planned
- kickoff is known
- the Match has not started
- no final result exists

A scheduled Match normally has:

- `kickoff`
- `homeClubId`
- `awayClubId`
- `competitionId`
- `seasonId`

and may have:

- `matchday`

The score should normally remain unset.

---

## Status: LIVE

`LIVE` means the Match is currently in progress.

The score may be known and updated during the Match.

For example:

Home: 1

Away: 0

A LIVE Match may therefore have:

`homeScore = 1`

`awayScore = 0`

Live score support does not require the initial Match model to store individual scoring events.

---

## Status: FINISHED

`FINISHED` means the Match has been completed and a final score is known.

A finished Match should normally contain:

- `homeScore`
- `awayScore`

Both values may be zero.

Therefore:

`0 - 0`

is a valid final score.

A missing score must not be interpreted as zero.

---

## Status: POSTPONED

`POSTPONED` means the Match will not take place at its currently scheduled kickoff.

The Match remains part of the same competition and season.

If a new kickoff is confirmed, the Match may be updated with:

- new `kickoff`
- appropriate status

For example:

`POSTPONED`

may later become:

`SCHEDULED`

with a new kickoff.

The Match identity remains unchanged.

---

## Status: CANCELLED

`CANCELLED` means the Match has been cancelled and is not currently expected to be played under the represented fixture.

A cancelled Match may have no score.

The system must not interpret cancellation as a 0–0 result.

---

## Status: ABANDONED

`ABANDONED` means the Match was abandoned before being completed.

The Match may have a partial score if one is known.

For example:

Home: 1

Away: 0

The score of an abandoned Match must not automatically be treated as the final competition result.

Any officially awarded result may require later correction or an additional result model.

---

## Score

The initial Match model stores the current canonical score using:

`homeScore`

and:

`awayScore`

Both fields are optional.

The score is therefore represented as two independent integer values rather than a formatted string.

Example:

```text
homeScore = 2
awayScore = 1
```

The frontend may display this as:

```text
2–1
```

but the formatted representation is not stored in the database.

---

## Score Semantics

A missing score means:

> No canonical score is currently known.

A score of zero means:

> The canonical score is explicitly zero.

Therefore:

```text
NULL
```

and:

```text
0
```

must not be treated as equivalent.

---

## Score Validity

Scores must be non-negative integers.

Valid:

```text
0 - 0
1 - 0
2 - 1
10 - 2
```

Invalid:

```text
-1 - 0
2 - -1
```

The domain must reject negative scores.

---

## Score and Match Status

For a `SCHEDULED` Match, scores should normally be unset.

For a `LIVE` Match, scores may be present.

For a `FINISHED` Match, both scores should normally be present.

For a `POSTPONED` or `CANCELLED` Match, scores should normally be unset.

For an `ABANDONED` Match, scores may be present if a partial score is known.

These are domain expectations rather than a requirement to encode every status/score combination as a rigid database constraint.

External sports data can contain incomplete or transitional states.

---

## Official Result

The initial Match model does not introduce a separate `officialResult` field.

The canonical score represents the currently accepted Match score.

If Kurvenfunk later needs to distinguish:

- live score
- final score
- officially awarded score
- provider-reported score
- corrected score

then a dedicated result/history model should be introduced rather than overloading the basic Match fields.

---

## Extra Time

The initial Match model does not store separate:

- regular-time score
- extra-time score
- penalty-shootout score

fields.

`homeScore` and `awayScore` represent the canonical score relevant to the current Match state.

Cup and knockout competitions may later require a dedicated result structure if detailed scoring phases need to be represented.

This keeps the initial Match entity focused on the common football fixture/result model.

---

## Penalty Shootout

Penalty shootout information is not part of the initial Match model.

A Match may therefore have:

- final football score
- additional shootout result

without requiring the initial Match entity to model every shootout penalty.

If required later, a dedicated Match Result model can represent:

- regular time
- extra time
- penalties

without changing the fundamental Match identity.

---

## Match Time History

The initial Match model does not store:

- actual kickoff time
- halftime time
- actual finish time
- previous kickoff times

Only the current canonical scheduled `kickoff` is required.

A future Match lifecycle/history model may store these values if operational or analytical requirements justify them.

---

## Match Lifecycle

A typical Match lifecycle is:

```text
SCHEDULED
    ↓
LIVE
    ↓
FINISHED
```

A scheduled Match may instead become:

```text
SCHEDULED
    ↓
POSTPONED
    ↓
SCHEDULED
    ↓
LIVE
    ↓
FINISHED
```

Other terminal outcomes include:

```text
SCHEDULED
    ↓
CANCELLED
```

or:

```text
SCHEDULED
    ↓
LIVE
    ↓
ABANDONED
```

The lifecycle must be interpreted according to normalized provider data and competition rules.

---

## Status Transitions

The domain should support at least the following transitions:

| From | To | Allowed |
|---|---|---|
| `SCHEDULED` | `LIVE` | yes |
| `SCHEDULED` | `POSTPONED` | yes |
| `SCHEDULED` | `CANCELLED` | yes |
| `LIVE` | `FINISHED` | yes |
| `LIVE` | `ABANDONED` | yes |
| `POSTPONED` | `SCHEDULED` | yes |
| `POSTPONED` | `CANCELLED` | yes |

Provider corrections may require additional transitions.

The domain implementation must not assume that external sports data is always perfectly chronological.

---

## Provider Independence

The Match entity is provider-independent.

It must not contain provider-specific fields such as:

```text
apiSportsId
sportmonksId
thesportsdbId
providerMatchId
providerStatus
```

Provider-specific information belongs to the import/provider domain.

The canonical Match should remain stable if:

- the sports provider changes
- multiple providers are used
- a provider is removed
- provider identifiers change

---

## Provider Matching

External provider records must be matched to the canonical Match through the sports import system.

The expected flow is:

```text
External Sports Provider
        ↓
Provider Adapter
        ↓
Normalization
        ↓
Validation
        ↓
Club Matching
        ↓
Competition Matching
        ↓
Season Matching
        ↓
Match Matching
        ↓
Canonical Match
```

The Match model itself does not implement provider matching logic.

---

## Provider Identifiers

Provider identifiers are not part of the canonical Match identity.

A future provider mapping model may store:

- provider
- external match identifier
- canonical match identifier
- first seen timestamp
- last seen timestamp
- matching status

This is intentionally outside Task 067.

---

## Duplicate Prevention

The system must prevent the same canonical Match from being created multiple times.

Match identity should be determined using the domain context rather than only provider data.

Important matching dimensions include:

- Competition
- Season
- Home Club
- Away Club
- scheduled kickoff
- provider evidence where available

The exact duplicate/matching algorithm belongs to the sports import domain.

---

## Match Identity and Kickoff Changes

A kickoff change must not automatically create a new Match.

For example:

```text
Rapid vs Sturm
2026-08-15 18:30
```

being moved to:

```text
Rapid vs Sturm
2026-08-16 17:00
```

is still the same Match.

The canonical Match identity remains unchanged.

---

## Rematches

Two different Matches between the same Clubs are valid.

For example:

```text
Rapid vs Sturm
```

may occur multiple times during one Season.

Therefore the following combination alone is not sufficient to identify a Match:

```text
homeClubId
awayClubId
seasonId
```

The Match model must allow multiple fixtures between the same Clubs within one Season.

This is particularly important for league competitions with home and away fixtures and for knockout competitions.

---

## Reverse Fixture

The reverse fixture:

```text
Sturm vs Rapid
```

is a different Match from:

```text
Rapid vs Sturm
```

Home and away roles are therefore part of Match identity.

The two Matches must remain separate canonical entities.

---

## Competition Format

The Match model must not assume that every Competition has:

- exactly two matches between Clubs
- numerical matchdays
- home and away legs
- league format

The initial model supports common league fixtures while remaining sufficiently generic for future competitions.

Competition-specific rules belong to the Competition domain.

---

## Club Lifecycle

A Club may later become inactive.

A Match must continue to reference the canonical Club.

Historical Matches must not be deleted merely because a Club becomes inactive.

For example, if a Club ceases to participate in current competitions, its historical Matches remain valid.

Therefore Match queries must not depend on:

`Club.active = true`

to determine whether a historical Match exists.

---

## Match Deletion

Canonical Matches should not be casually deleted after being referenced by other domain entities.

Articles, discussions, standings, imports, and historical records may reference Matches.

If an imported Match was created incorrectly, the preferred approach is correction or controlled removal through the relevant administrative/import workflow.

A generic soft-delete field is not required by the initial Match model.

---

## Article Relationship

Articles may later reference a Match.

For example:

```text
Rapid defeats Sturm 2–1
```

The article can reference the canonical Match rather than storing duplicated fixture data.

The Article domain owns the article-to-Match relationship.

The Match model does not contain article identifiers.

---

## Discussion Relationship

A Match may later have a discussion associated with it.

The Match domain does not directly own comments or forum posts.

Community entities may reference the Match where required.

This keeps football data separate from community content.

---

## Standing Relationship

Standings may be calculated from completed Match results.

The Match model provides:

- home Club
- away Club
- final score
- competition
- season
- match status

The Standing model determines how those values affect league tables.

The Match model itself does not store:

- points awarded
- wins
- draws
- losses
- goal difference

Those are derived or stored by the Standing domain.

---

## Standings Eligibility

Not every Match status should automatically contribute to standings.

In particular:

- `SCHEDULED` does not contribute
- `LIVE` does not represent a final result
- `POSTPONED` does not contribute
- `CANCELLED` does not automatically contribute
- `ABANDONED` requires competition-specific handling
- `FINISHED` is normally eligible

The Standing calculation must apply competition rules rather than assuming every score is a valid league result.

---

## Matchday Queries

The Match model must support efficient queries such as:

- all Matches for a Season
- all Matches for a Competition
- all Matches for a Club
- all upcoming Matches
- all finished Matches
- all Matches on a specific matchday
- all Matches within a kickoff range
- all Matches for a Club in a specific Season
- all Matches for a Competition on a specific matchday

Appropriate database indexes will be added when the Prisma schema is implemented.

---

## Expected Indexes

The eventual Prisma/database implementation should consider indexes for:

```text
homeClubId
awayClubId
competitionId
seasonId
kickoff
status
matchday
```

Composite indexes should be considered for common access patterns such as:

```text
seasonId + kickoff
competitionId + seasonId + kickoff
homeClubId + kickoff
awayClubId + kickoff
seasonId + matchday
```

The final index design belongs to Task 081 when the complete Prisma schema is created.

---

## Upcoming Match Queries

Upcoming Matches should generally be queried using:

- Match status
- kickoff
- competition/season
- club

A Match with a future kickoff is not necessarily `SCHEDULED` if external data explicitly reports another state.

Status is authoritative for lifecycle state.

Kickoff is authoritative for temporal ordering.

---

## Past Match Queries

Historical Match pages should primarily use:

- `FINISHED`
- `ABANDONED`
- other explicitly relevant terminal statuses

rather than simply checking whether `kickoff < now`.

A future kickoff may belong to a postponed or cancelled Match.

Therefore status and time must not be conflated.

---

## Match Ordering

For fixture lists, Matches should normally be ordered by:

```text
kickoff ASC
```

For historical results:

```text
kickoff DESC
```

The API layer defines the final sorting contract.

The database model only provides the fields required to support efficient ordering.

---

## Nullability

The following fields are required:

- `id`
- `homeClubId`
- `awayClubId`
- `competitionId`
- `seasonId`
- `kickoff`
- `status`
- `createdAt`
- `updatedAt`

The following fields are optional:

- `matchday`
- `homeScore`
- `awayScore`

`matchday = NULL` means that no numerical matchday is applicable or currently known.

`homeScore = NULL` and `awayScore = NULL` mean that no score is currently known.

---

## Score Pair Consistency

The score fields form one logical value.

The system should avoid states where only one side has a score.

For example:

```text
homeScore = 2
awayScore = NULL
```

should normally be considered invalid for the canonical Match score.

The application/domain layer should validate that either:

```text
homeScore = NULL
awayScore = NULL
```

or:

```text
homeScore >= 0
awayScore >= 0
```

are present together.

An exception may be required during provider import normalization before data reaches the canonical domain.

---

## Matchday Validation

If `matchday` is provided:

```text
matchday >= 1
```

is expected.

Zero and negative matchdays are not valid for the initial model.

The field remains nullable because some competitions do not use numerical matchdays.

---

## Immutable Fields

The following values represent core Match identity/context and should normally not change after creation without controlled correction:

- `id`
- `homeClubId`
- `awayClubId`
- `competitionId`
- `seasonId`

Kickoff and status may change during the Match lifecycle.

Score may change during live updates and until the canonical final result is established.

---

## Corrections

Sports provider data can be corrected after initial import.

The domain must therefore allow controlled updates to:

- kickoff
- matchday
- status
- homeScore
- awayScore

Corrections must be logged through the relevant import/audit mechanisms where appropriate.

The Match entity itself does not need to contain an audit history.

---

## Match Import

Sports imports may:

1. discover a new Match
2. match it to an existing Match
3. update kickoff
4. update status
5. update score
6. correct previously imported data

The import system must never create duplicate Matches merely because the provider sends updated information.

---

## Raw Provider Data

Raw provider payloads must not be stored directly in the Match entity.

Raw data belongs to the Import domain.

This allows Kurvenfunk to:

- reproduce import problems
- inspect provider changes
- re-run normalization
- change provider adapters

without polluting the canonical football domain.

---

## Match and Club Aliases

Club matching during imports may use the Club Alias model.

Example provider values:

```text
Rapid Wien
SK Rapid
Rapid
SCR
```

may all resolve to:

```text
canonical Club
```

The resulting Match stores only:

```text
homeClubId
```

or:

```text
awayClubId
```

The provider's original Club name remains part of the import/raw data context.

---

## Match and Competition Matching

The same provider-independent principle applies to Competition.

Provider competition names must be normalized before creating or updating a canonical Match.

The Match stores:

```text
competitionId
```

rather than provider-specific competition names.

---

## Match and Season Matching

The Match must belong to the canonical Season.

Sports import processing must determine the correct Season before accepting the Match into the canonical domain.

A Match must never be created merely because a provider supplied an arbitrary season label.

---

## Timezone Policy

The Match domain stores absolute timestamps.

Display timezone is a presentation concern.

The backend must not store kickoff as an ambiguous local-time string.

The canonical value must preserve timezone/instant information.

This is especially important because Kurvenfunk may later expand beyond Austria.

---

## International Expansion

The Match model must not assume:

- Austrian timezone
- Austrian competitions
- Austrian date formats
- Austrian Club naming
- Austrian matchday conventions

A Match is a generic football domain entity.

The initial data will focus on Austrian competitions, but the model must support future expansion.

---

## Match Status and Provider Status

External providers may use different status systems.

Examples may include:

```text
NS
TBD
1H
HT
2H
FT
PST
CANC
ABD
```

These provider-specific values must be normalized into the canonical Kurvenfunk `MatchStatus`.

Provider status is therefore not stored directly on Match.

---

## Live Data

The initial Match model supports the basic state required for live matches:

```text
status = LIVE
homeScore
awayScore
```

It does not attempt to model live event streams.

Future live functionality may introduce:

- goals
- cards
- substitutions
- VAR events
- periods
- minute
- added time
- lineups

These should be separate domain concepts.

---

## Match Events

Match events are explicitly outside Task 067.

A future Match Event model may reference:

```text
matchId
```

and represent events such as:

- goal
- own goal
- penalty
- yellow card
- red card
- substitution

The Match entity should not become a large container for every event occurring during a football match.

---

## Venue

Venue information is outside the initial Match model.

A future Venue model may be introduced if Kurvenfunk needs:

- stadium
- location
- capacity
- address
- coordinates

The Match should then reference the canonical Venue.

No `venueName` field is required for Task 067.

---

## Referee

Referee information is outside the initial Match model.

No referee field is required.

---

## Player Data

The Match model does not directly reference individual players.

Player-related Match data belongs to future sports-data models.

---

## Match URL / Slug

The initial domain model does not require a persisted Match slug.

A frontend route may later derive a stable URL representation from:

- Match ID
- Clubs
- kickoff

If SEO requirements require a canonical slug, that decision can be made when Match pages are implemented.

---

## Public Match Representation

A public Match representation may expose:

- Match ID
- home Club
- away Club
- kickoff
- Competition
- Season
- matchday
- status
- score

Provider-specific information must not leak into the public domain representation.

---

## Administrative Match Representation

Administrative interfaces may additionally expose:

- provider mappings
- import state
- raw provider references
- matching confidence
- correction history

These are import/admin concerns and should not be added to the core Match entity simply for administrative display.

---

## Security

Match data is not considered private user data.

Normal Match reads may therefore be public.

Administrative correction operations require appropriate permissions.

The Match model does not itself define authorization rules.

---

## Audit

Creating or modifying Match data through administrative correction workflows may require audit logging.

Automated provider imports do not necessarily require a human moderation audit entry for every update.

Import history should be handled by the Import domain.

---

## Source of Truth

PostgreSQL is the source of truth for canonical Match data.

Redis may cache Match data.

Meilisearch may index Match-related searchable content in the future.

Neither Redis nor Meilisearch may become the authoritative source of Match data.

---

## Caching

Match data may be cached where useful.

Potential cache candidates include:

- upcoming fixtures
- recent results
- club fixture lists
- competition fixture lists
- matchday schedules

Cache entries must always be reconstructable from PostgreSQL.

---

## Search

The initial Match model does not require a dedicated Meilisearch Match index.

Match information can initially be queried through PostgreSQL.

If later search requirements justify indexing Matches, the index must be reconstructable from PostgreSQL.

---

## API Considerations

The eventual Match API should be able to support:

- Match detail
- upcoming Matches
- recent results
- Club fixtures
- Competition fixtures
- Season fixtures
- matchday fixtures

The API must not expose provider-specific implementation details unless explicitly requested by an administrative endpoint.

---

## Validation Rules

The canonical Match domain must enforce at least:

1. `homeClubId` is required.
2. `awayClubId` is required.
3. Home and away Club must be different.
4. `competitionId` is required.
5. `seasonId` is required.
6. Season must belong to Competition.
7. `kickoff` is required.
8. `status` is required.
9. `matchday`, when present, must be a positive integer.
10. Scores, when present, must be non-negative integers.
11. Home and away score must be provided together.
12. Provider-specific identifiers do not define Match identity.
13. A kickoff change does not create a new Match.
14. Duplicate fixtures must be prevented by domain matching rules.

## Domain Invariants

The following invariants define a valid Match:

### Invariant 1

A Match has exactly one home Club.

### Invariant 2

A Match has exactly one away Club.

### Invariant 3

Home and away Club are different.

### Invariant 4

A Match belongs to exactly one Competition.

### Invariant 5

A Match belongs to exactly one Season.

### Invariant 6

The Season belongs to the Match's Competition.

### Invariant 7

A Match has exactly one canonical kickoff value.

### Invariant 8

A Match has exactly one canonical status.

### Invariant 9

A score consists of zero or one complete home/away score pair.

### Invariant 10

Scores cannot be negative.

### Invariant 11

Provider identifiers do not define the canonical Match identity.

### Invariant 12

Changing the scheduled kickoff does not by itself create a new Match.

## Design Principles

### Provider-independent

The Match represents Kurvenfunk's canonical football data.

### Stable identity

Provider changes and kickoff changes must not unnecessarily create new Matches.

### Explicit status

Lifecycle state is represented explicitly and not inferred only from dates.

### Explicit score

Scores are numeric values and are not stored as formatted strings.

### Historical integrity

Historical Matches remain valid even when Clubs become inactive.

### Competition-aware

Every Match belongs to a specific Competition and Season.

### Reconstructable

Canonical Match data lives in PostgreSQL and can be used to rebuild caches and indexes.

### Extensible

Future live and detailed football data should be added through separate domain concepts.

## Final Decisions

1. Match is a canonical Kurvenfunk domain entity.
2. Match identity is provider-independent.
3. Every Match has one home Club.
4. Every Match has one away Club.
5. Home and away Club must be different.
6. Every Match belongs to one Competition.
7. Every Match belongs to one Season.
8. The Season must belong to the Match's Competition.
9. `kickoff` represents the current scheduled kickoff instant.
10. Kickoff is stored as an absolute timezone-aware timestamp.
11. A kickoff change does not create a new Match.
12. `matchday` is optional.
13. `matchday`, when present, must be a positive integer.
14. Match status is explicit.
15. Initial statuses are `SCHEDULED`, `LIVE`, `FINISHED`, `POSTPONED`, `CANCELLED`, and `ABANDONED`.
16. Scores are stored as numeric home/away values.
17. Scores may be absent when no canonical score is known.
18. Home and away score must be present together.
19. Scores cannot be negative.
20. `0 - 0` is a valid score and is distinct from an unknown score.
21. Finished Matches normally have a complete score.
22. Postponed and cancelled Matches are not interpreted as 0–0 results.
23. Abandoned Match scores are not automatically treated as official results.
24. Extra-time and penalty-shootout details are outside the initial Match model.
25. Match events are outside the initial Match model.
26. Provider identifiers belong to the provider/import domain.
27. Raw provider payloads belong to the import domain.
28. Club matching uses the canonical Club and Club Alias models.
29. Competition and Season matching uses the canonical Competition and Season models.
30. Multiple Matches between the same Clubs in one Season are allowed.
31. Reverse home/away fixtures are separate Matches.
32. Historical Matches remain valid when a Club becomes inactive.
33. Match does not own articles, comments, forum posts, or standings.
34. PostgreSQL is the source of truth for canonical Match data.
35. Redis and Meilisearch must remain reconstructable from PostgreSQL.
36. The eventual Prisma implementation belongs to Task 081.
37. No migration is created as part of Task 067.
