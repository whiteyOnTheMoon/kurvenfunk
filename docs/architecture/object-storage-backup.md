# Object Storage Backup Strategy

## Status

Task 055 – Object Storage Backup Strategie

## Scope

Kurvenfunk uses object storage for binary media files such as editorial
images, user uploads and avatars.

Development and staging currently use MinIO.

Production is planned to use Cloudflare R2.

PostgreSQL stores references and metadata for media objects, but the binary
objects themselves are stored in object storage. Therefore PostgreSQL backups
alone are not sufficient to restore the complete application state.

## Principles

1. Non-reproducible original files must be recoverable independently from the
   primary object storage.

2. Object-storage backups must be logically separated by environment.

3. Production backup data must not depend exclusively on the same storage
   location or bucket as production.

4. Reproducible derivatives do not necessarily require backup if they can be
   regenerated reliably from their original objects.

5. Redis and Meilisearch data are outside the scope of this strategy because
   they are reconstructible and are not object storage.

## Data Classification

### Must be backed up

The following objects are considered non-reproducible and must be protected:

- original editorial media uploads
- original user uploads
- user avatars
- original images associated with articles
- manually uploaded club or competition media
- other binary assets that cannot reliably be recreated from another source

### Backup optional / reconstructible

The following data does not require an independent backup when reliable
regeneration exists:

- thumbnails
- resized images
- optimized image variants
- temporary upload files
- caches
- generated previews
- other derived media generated from an existing original

Applications should clearly distinguish original objects from generated
derivatives in their storage keys or metadata.

## Development

Development uses MinIO under:

`/srv/kurvenfunk/dev/minio`

Development object storage contains disposable development and test data.

No automated long-term object-storage backup is required for DEV.

Important test fixtures that need to survive environment recreation should be
stored in the repository or regenerated by seed/test tooling instead of relying
on MinIO persistence.

## Staging

Staging uses MinIO under:

`/srv/kurvenfunk/staging/minio`

Staging is not permitted to contain the only copy of important production
assets.

When staging starts containing persistent manually created media, original
objects should be included in automated object-storage backups.

Staging backup data must remain separate from production backup data.

## Production

Production will use Cloudflare R2 as its primary object storage.

Production original objects require protection against:

- accidental deletion
- application bugs
- compromised credentials
- destructive administrative actions
- provider-side or account-level incidents

Production must therefore have an independent backup copy of all
non-reproducible original objects.

Bucket versioning, retention features or deletion protection may be used as an
additional safety layer where available, but they do not replace an independent
backup copy.

The independent copy should use separate credentials and preferably a separate
failure domain from the primary production bucket.

## Backup Frequency

Object storage does not require database-style point-in-time consistency.

The target policy is:

- backup or replicate new production originals at least daily
- preferably copy new immutable originals shortly after successful upload
- perform a regular reconciliation to detect missing objects
- staging may use a daily backup when relevant persistent objects exist
- DEV has no scheduled object-storage backup requirement

The exact automation will be implemented together with the backup/restore
tooling.

## Retention

Original media should normally be retained for at least as long as the
corresponding application record exists.

Backup retention must protect against delayed discovery of accidental deletion.

Deletion from the primary storage must therefore not immediately delete the
last backup copy.

A concrete retention period will be finalized before production launch based on
storage cost, privacy requirements and media lifecycle rules.

## Security

Backup credentials must:

- be separate from application credentials where possible
- follow least-privilege permissions
- never be stored in Git
- be stored in environment-specific protected configuration

Backup storage must not be publicly readable.

Transport to remote object storage must use encrypted connections.

## Integrity

Backup automation should verify that objects were copied successfully.

Periodic reconciliation should compare at least:

- storage key
- object existence
- size

Checksums should be used where supported and practical.

Backup jobs must fail visibly when objects cannot be copied or verified.

## Monitoring

Object-storage backup failures must eventually be integrated into the general
backup monitoring defined by Task 278.

Relevant failures include:

- authentication errors
- inaccessible source storage
- inaccessible backup destination
- incomplete copies
- integrity mismatches
- insufficient storage capacity

## Restore

Restore implementation is intentionally not part of Task 055.

Task 056 will provide restore tooling.

Task 057 will verify the restore process against an empty test environment.

A backup is not considered operationally valid until its restore path has been
tested.

## Current State

At the time this strategy was introduced:

- DEV MinIO bucket: `kurvenfunk-media`
- STAGING MinIO bucket: `kurvenfunk-media`
- DEV contains no user/media objects
- STAGING contains no user/media objects
- Production R2 is not yet active
- no existing object-storage backup needs migration

This means the strategy is being introduced before persistent application media
is created.
