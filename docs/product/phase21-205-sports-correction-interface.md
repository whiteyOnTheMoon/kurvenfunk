# Phase 21.205 – Sports Correction Interface

## Goal and separation

An **administrator-only** interface for reviewing and correcting provider-specific
sports club and match mappings generated by tasks 21.201–21.204. It is mounted
within **Admin → Sportdaten**. This is an editorial mapping decision, **not**
a direct edit of canonical `Club`, `Match`, scores, fixtures or standings.
No sports data provider is activated and no import is automatically started.

The existing Prisma `EntityMatch`, `ImportRecord` and `AuditLog`
models already represent review identity, history and actors, so **no migration**
or database model change is required.

## API contract

All routes use `@RequirePermissions(PERMISSIONS.SPORTS_CORRECTION_MANAGE)`,
which is assigned to `ADMIN` and `SUPERADMIN` **only**. JWT, active user
status and the Nest permissions guard are the authoritative access check.
An editor, moderator, unauthenticated or limited/banned account may not
invoke this correction interface. Every route is protected, including reads.

- `GET /api/v1/imports/sports/corrections?status=review|all&limit=30`:
  at most 50 newest provider-scoped `CLUB`/`MATCH` mapping records for
  `provider.type=SPORTS`. `review` shows open/ambiguous/unmatched records;
  `all` includes prior accepted/rejected decisions. Excludes news mappings.
- `GET /api/v1/imports/sports/corrections/candidates?entityType=CLUB|MATCH&q=...`:
  at most 20 candidates from existing canonical records, searching active
  club names or fixtures by home/away club names (also match UUID).
- `POST /api/v1/imports/sports/corrections/:uuid`:
  discriminated, strict payload. `decision=MATCH` **requires** a valid target
  UUID; `decision=REJECT` cannot supply one. Both require a rationale of
  10–500 characters and `expectedUpdatedAt` from the list response.
  This optimistic version check protects against overwriting another
  administrator's recent change. Invalid requests are rejected.

Example:
```json
{
  "decision": "MATCH",
  "targetId": "33333333-3333-4333-8333-333333333333",
  "expectedUpdatedAt": "2026-11-09T18:00:00.000Z",
  "reason": "Identität anhand der offiziellen Spielansetzung geprüft"
}
```

## Validation and audit safety

The correction runs within a serializable PostgreSQL transaction. It acquires
the same provider/external-ID advisory lock used by the sports worker (202
for CLUB, 203 for MATCH), preventing racing automatic/imported updates.
When matching to a canonical target it additionally locks the target identity.
An existing CLUB must still be active. A MATCH must exist with active and
distinct participating clubs and a consistent season/competition. The same
provider may not bind two different external match IDs to one canonical
match. Rejected or stale updates fail closed with an HTTP conflict response.

The transaction updates the provider's `EntityMatch` to
`MATCHED + MANUAL` or `REJECTED`, records `reviewedById` and
`reviewedAt`, and updates only **unreviewed** staged sport import records
for the same provider/external ID. Previously reviewed import records
remain unchanged. The same transaction writes an `AuditLog` row using
`ADMIN_CORRECTION` with reviewer, rationale, former status/target, decision
and affected record count. If the audit insert fails, the transaction rolls
back. No raw provider content or credentials are copied into audit metadata.

A later worker retry respects manually matched IDs/rejections and cannot
silently overwrite reviewed decisions. Any future manual re-correction
requires another explicit admin request, reason and audit entry.

The existing `/imports/review-queue` and generic approve/reject endpoints are
**editorial news-only**, including the reject path. This closes the previous
possibility of using news review to dismiss sports records without the
dedicated sports correction permission.

## UI and limits

The admin UI shows open and all status filters, provider/source identifiers,
the current target, target candidate search, a decision selector, mandatory
reason, explicit confirmation and separate success/error feedback. It does
not expose a free-form canonical UUID submission without finding/selecting
an existing target. Users with no administrative role cannot render actions;
the backend permission guard remains essential.

The initial bounded list is the **50 most recently updated mappings**, and
candidate search is capped at 20. Pagination, additional evidence tooling and
batch corrections are intentionally deferred until a concrete operational need.

## Verification and operational boundaries

Unit tests cover admin authorization, news/sports review separation,
successful and rejected decisions, canonical target validation, duplicate
fixture protection, optimistic version conflicts, audit persistence and
serializable retry. Frontend role visibility tests and repository CI checks
must pass before merging. After merge, verify DEV deployment and safe branch
cleanup.

**The real isolated Redis/PostgreSQL end-to-end sports-import acceptance from
21.201 remains open.** This correction interface does not mark it done.
STAGING/PROD changes, real provider activation, automatic result publication
and standings recalculation are not part of this task.
